## Verdict
No objection to dismissing the Important finding, but on the ground that the appended code was checked for the ways an append-only diff can still weaken a suite, not on the ground that "it only adds lines".

## The case against
The easy answer is "the diff only appends to `tests/test_data.py`, so the rule is not breached". That ground is weak on two counts.
First, REVIEW.md's text is literal: "must not modify test files that existed before the fix". `tests/test_data.py` existed at the merge base (`071cd24`) and is modified (hunks at lines 2 and 498). Read literally, the only compliant place for the regression tests was a new file, and the deterministic check (source `framework`, build guide step 25) flagged exactly that; a review that waves it through on "additions do not count" rewrites the owner's rule in a run.
Second, "append-only" is not "harmless": an appended `def test_<existing name>` silently replaces the earlier test at collection, an appended autouse fixture or a shadowing module-level import changes what every pre-existing test sees, and none of those shows as a modified line. The deterministic check cannot tell these from a benign append, which is why it reports Important and leaves the judgement to the reviewer.
What answers both: the rule's own second clause ("the failing test written first is the proof") and the intent, spec and plan all name `tests/test_data.py` as the home of the regression tests, and `CLAUDE.md` requires one test module per area, so a new file would breach the project convention the rule sits beside. The hunks are additions only (`@@ -498,3 +504,59 @@`, context lines unchanged); each of the four new names occurs once in the file; the seven new imports (`email.message`, `io`, `urllib.*`, `Callable`) shadow nothing the existing tests use (`http` is still the `app.data` module); no autouse fixture or conftest was added; the case count went 69 -> 89 = 69 + 20 new parameter sets, so no pre-existing case vanished. The additions landed in the first, reproducing commit (`failing-test.log`: 20 failed on `main` with `app/` unchanged) and the `test_lock` check passed at both the build and test gates against lock commit `047eba15`.
I would decide: close the finding as not a breach, recording those checks as the reason, and keep the companion nit (`d47002cb`) as the owner's prompt to tighten REVIEW.md's wording to "must not change or remove a test that existed before the fix" so the next fix-type change does not raise the same false Important. What would make me accept the easy answer outright: that wording change by the owner.
