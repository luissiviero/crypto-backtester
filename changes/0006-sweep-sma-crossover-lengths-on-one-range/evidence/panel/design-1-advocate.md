## Verdict
No objection to accepting argparse's refusal and not rewriting argv, but the concern's premise is false (the behaviour is not Python-version dependent) and both two-word forms are deterministic and must be pinned by tests before build; the text should be corrected.

## The case against
The concern says `--fast -5,10` "may be read by argparse as an option ... depending on the Python version's negative-number rule" and that `run` behaves so for `--fast -5` "on the versions where argparse reads it as an option". Today's code contradicts both halves. `tests/test_backtest_cli.py` line 114 already passes `["--slow", "-5"]` as two words and expects `slow -5 is not a whole number of at least 1`; it is green on CI (Python 3.12). argparse treats a bare `-5` as a value on every Python since 2.7 whenever the parser defines no option that itself looks like a negative number, which `run` does not and the planned `sweep` will not. There is no version on which `run --fast -5` reaches argparse's error.
The other half is equally fixed: `-5,10` never matches argparse's negative-number pattern (`^-\d+$|^-\d*\.\d+$`; 3.13's variant adds underscores, not commas), so a two-word `--fast -5,10` is an unknown option on every version and always ends in usage plus `error: argument --fast: expected one argument`, exit 2. The real split is bare negative (reaches `_lengths`, gets the R4 message) versus comma list starting with a minus (argparse refuses), not Python version.
Why it matters: (1) the spec carries a false claim about today's code into build, the case angle 8 exists for; (2) because the behaviour was called uncertain, plan.md's `test_sweep_refuses_bad_lengths` tests only `--fast=-5,10` and neither two-word form, so a build that accidentally gave `--fast -5` argparse's message, or named no value, would still pass; (3) R12 promises "one `error: ...` line on stderr" for every refusal, which argparse's usage-plus-error output breaks; Acceptance carves out `--market` but not this case.
The resolution itself is sound: the input is invalid either way, exit code is 2 either way, `--fast=-5,10` is a documented escape, and an argv rewrite for an input that can never be valid is more code than the case deserves. I would decide the same and change only the record: restate the concern as the deterministic rule above; add two cases to `test_sweep_refuses_bad_lengths`, two-word `--fast -5` expecting `fast -5 is not a whole number of at least 1` with no stub call, and two-word `--fast -5,10` expecting `SystemExit` 2 with `expected one argument` on stderr, as `test_run_refuses_bad_market` pins argparse; and let R12 name argparse's refusals as the exception to the one-line rule. With those text and test additions, no design change, I accept the obvious resolution.
