## Verdict
Object to the deferred range check: refuse a bad `--fee` before `load_klines`, reusing the engine's own `_check_fee` so no rule is copied, and have the bad-fee test assert the stub saw no call.

## The case against
The design keeps the intent's letter ("passed to `run_backtest`", refused "before any backtest") but breaks the one property every other refusal in this CLI and in the CLI it mirrors has: nothing is downloaded or written until every argument is accepted. `app/data/__main__.py:_download` calls `make_request` first and touches the network only after; the design checks symbol, dates, lengths and the fee's *type* first, then lets `--fee 1.5`, `--fee -0.1`, `--fee nan` and `--fee inf` (all pass `float()`) run the whole `sync_days` pass, paged requests under `RateLimitPacer`, writing day files to the cache (`loader.py:122`), and only then exit 2. For 1m candles over months that is minutes of network and disk side effects on an input the engine refuses in its first line (`inputs.py:29`). Security-baseline rule 2 (validate every input before it is used) and coding-standards rule 2 (match `download`'s error handling) are the rules this bends, even if neither names the case.
The stated reason, "it would copy the engine's `0 <= fee < 1` rule into a second place", is thinner than it reads: the rule already exists once in `inputs._check_fee`, the CLI already imports `DEFAULT_FEE` and `BacktestInputError` from `inputs`, and the plan's `_fee` helper can simply `return _check_fee(float(text))`. `inputs.py` stays unchanged (R14), the message stays the engine's, and no second rule exists anywhere.
The plan's `test_run_refuses_bad_fee` cannot tell the two designs apart: it asserts stderr and exit 2 only. `tests/kucoin_stub.py` records every URL in `calls`, yet neither spec nor plan asserts `calls == []` for the fee cases, so the order the owner decides here is unpinned and can drift silently at build or later.
In fairness: the download is not wasted (the days are cached, the corrected re-run reads them), the intent lists the fee after the load-dependent refusals, and the engine would still refuse the fee before any arithmetic. I would accept the obvious resolution if the owner says a one-off cached download on a typo is fine, and the plan then pins the chosen order with a `calls` assertion in the bad-fee test either way, so the behaviour is a decision and not an accident of call order.
