## Verdict
Return `None` (field `float | None`) when `trade_count == 0`, not `0.0`; accept `0.0` only if `Summary.win_rate`'s docstring says so and the test pins it together with `trade_count == 0`.

## The case against
The intent (line 43) defines win rate as "the share of trades whose return after fees is above zero". A share of an empty set is undefined; `0.0` is the value of a different state, "every trade lost". The design collapses the two: a strategy that never traded and one that traded five times and lost five times read the same on this field, and the spec's own remedy ("no trades is read from `trade_count == 0`") admits the field cannot be read alone. That is a sentinel, which the intent's "short summary" the owner reads did not ask for.
The spec pairs it with "max drawdown on a flat curve is `0.0`", but those are not alike: a flat curve genuinely never fell, so `0.0` is the computed value; no trades yields no value at all.
The project's own idiom for "absent" is `None`, not a sentinel: `app/data/loader.py` has `_first_day(frame) -> date | None` returning `None` on an empty frame, `Gap.reason: str | None`, and `rest.py` returns `pl.DataFrame | None`. Polars itself gives null for the mean of an empty series. Coding-standards rule 2 (match the surrounding code) points to `None`; the common backtesting libraries report NaN here for the same reason.
The plan's two reasons for rejecting the alternative are thin: "NaN fails equality checks" argues against NaN only, and "it would make the field `float | None`" names the annotation as if it were a cost. `None` compares with `==` in a test and reads as "undefined" without a second lookup.
A `0.0` that is a legal value also hides an engine bug: if the pass silently drops every trade (the plan's own riskiest step), the summary stays well formed (0 trades, win rate `0.0`, a non-zero total return) and no single-field assertion flags it; a `None` turns any downstream arithmetic on it into a visible failure.
I would decide: `win_rate: float | None`, `None` when `trade_count == 0`, and rename the Proof test to say "win rate is None". I would accept the design's `0.0` if the owner prefers an all-numeric record for later tabulation, provided the `Summary` docstring states "0.0 when there are no trades; see `trade_count`" and `test_no_trades_gives_zero_win_rate_and_flat_equity` asserts `trade_count == 0` and `win_rate == 0.0` together, so the convention is written down and not inferred.
