## Verdict
Keep the `pyproject.toml` edit, but not in its easy form: name the proof for it (a wheel listing in the build verifier, as change 0002's verifier did) and prefer `[tool.setuptools.packages.find] include = ["app*"]` over a third hand-kept entry, so this concern is not re-filed by every later package; if the owner would rather honour the intent's "needs no change" line, leaving the file untouched is safe for every install this project actually performs.

## The case against
The easy answer is "one line in a non-guardrail file, obviously harmless". Four things weigh against it as written.
1. It contradicts a line the owner merged (intent.md: "`pyproject.toml` and `.github/workflows/ci.yml` need no change"), and the design does not say the owner is asked to re-decide it; it just proceeds. A merged intent line should be overturned by the owner at the gate, not quietly by the spec.
2. Nothing in Proof checks it. plan.md's test list has no wheel or install test, and `tests/test_backtest.py` imports `app.backtest` from the checkout, so every test passes with the entry present, absent or misspelt. Change 0002 proved the same table with `pip wheel` and a listing of the wheel's files (its verifier.md, "Packaging"); this plan does not ask the build verifier for that, so the one claim the edit makes ("a regular install ships the new package") stays a claim.
3. The benefit is for a consumer that does not exist. `commands.setup` is `pip install -e .`; the project's own CI (`.github/workflows/ci.yml`) never installs the package at all, it runs `python -m pytest` from the checkout; the intent names the owner's own scripts as the only consumer. The cost, named in plan.md's Risks, is that a typo breaks `pip install -e .` for every SDLC phase job (not the project CI, which plan.md wrongly includes).
4. It treats the symptom. The list exists only because change 0002 silenced flat-layout discovery ("Multiple top-level packages discovered"); appending `"app.backtest"` keeps a hand-kept list that every future package (strategies, a CLI, shorts) must remember, each time as a flagged concern. `packages.find` with `include = ["app*"]` is also one line, removes the contradiction for good, and still excludes `changes/`, `evals/`, `lessons/`, `policies/`.
What I would decide: make the packaging line self-maintaining (`find`/`include = ["app*"]`), and add to Acceptance that the build verifier builds a wheel and lists `app/backtest/*.py` in it. I would accept the obvious one-entry edit if the owner's design-gate merge is recorded as the decision that overrides the intent line and the build verifier's wheel listing is named as its proof; the edit itself is correct in substance.
