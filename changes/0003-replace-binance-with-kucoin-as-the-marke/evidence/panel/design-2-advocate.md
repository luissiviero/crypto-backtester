## Verdict
Accept 100 / 60 s as the constants, but reject the claim that closes the concern ("a wrong value costs speed or a 429, which the retries absorb"): make the 429 path read `gw-ratelimit-reset` when `Retry-After` is absent, and say so in R4, plan step 3 and a Proof test.

## The case against
The easy answer is that the reserve is a tunable guess and a miss is harmless because `with_retries` absorbs a 429. Today's code says otherwise: `RETRY_DELAYS = (1.0, 2.0, 4.0)` (`app/data/http.py`), so without a `Retry-After` the three retries span about 7 s, while KuCoin's pool is a 30 s window (`gw-ratelimit-reset` up to 29999 ms in `references/capture/summary.json`). A pool emptied by anything else on the owner's IP therefore gives 429 on every retry and ends in `DownloadError` in under ten seconds, not in a wait. No captured answer is a 429 and none carries `retry-after` (the capture kept that header; it never appeared), so "`Retry-After` honoured" rests on nothing measured. The owner's own `kucoin_capture.py` did not trust it either: `_wait_seconds` sleeps `gw-ratelimit-reset` on a 429, which the design drops.
This matters more than under Binance: Vision is gone, so a year at 1m is ~2,600 sequential REST pages, and a `DownloadError` ends the run (and, as the panel's item 3 notes, discards the range's pages). The reserve is then the only guard between a shared pool and a dead run, and the pacer reads only the previous answer, so it cannot see a drain that happens between two calls. Alone, the program never reaches 100 anyway (one call at a time, cost 3 of 2000 per 30 s): the reserve protects nothing in the single-process case and under-protects the shared case the spec invokes to justify it. The design also ignores `gw-ratelimit-limit`, present on every captured answer, while deriving the reserve from an assumed 2000.
I would decide: keep `RATE_LIMIT_RESERVE = 100` and `MAX_RATE_LIMIT_WAIT = 60.0` as module constants; in `with_retries`, when a 429 has no usable `Retry-After`, wait `gw-ratelimit-reset` ms bounded to `MAX_RATE_LIMIT_WAIT` (the capture script's rule); add `test_429_without_retry_after_waits_for_the_reset` to Proof; reword the plan's Risks line to drop "which the retries absorb".
I would accept the obvious resolution if the owner shows a captured KuCoin 429 with a `Retry-After` header, or states that a `DownloadError` on a shared-IP drain is acceptable and the Risks line is corrected to say so.
